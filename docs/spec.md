# CRM Enrichment via treg.to

**Status:** In progress — Phases 1–2 implemented (profile enrichment for people and companies); Phase 3a implemented for hiring and news; Phase 3d (similar companies) implemented
**Date:** 2026-10-05
**Scope:** OSS — standalone provider package `open-mercato-enrichment-treg`, released from [`Chmarusso/open-mercato-enrichment-treg`](https://github.com/Chmarusso/open-mercato-enrichment-treg)

> **Moved 2026-10-08.** The package was first built in `open-mercato/official-modules` as `@open-mercato/enrichment-treg` (PR #57). That repo is deprecated and the maintainers asked for paid third-party integrations to be released by their owners, so the package now lives in its own repo under the name above. The "Release via Official Modules" section below is kept for history.

## TLDR

Add a standalone integration provider package that enriches CRM people and companies with profile data and signals (hiring, news), and finds companies similar to an existing CRM company, all fetched through [treg.to](https://treg.to). Enrichment is triggered manually (detail-page button or list bulk action), runs in a queue worker, and produces **proposals** that a user reviews and accepts before anything is written to the CRM. No changes to `packages/core`. The package lives in and ships from the `open-mercato/official-modules` repo, and users install it with `yarn mercato module add @open-mercato/enrichment-treg`.

## Overview

treg.to is a pay-per-call gateway in front of ~108 data providers. One org token (`X-Treg-Token`) and one call shape (`POST https://treg.to/call/{endpoint-id}`) reach every provider; routed `treg.*` endpoints pick the provider per call (org keys first, then cheapest) and report which one served the request. Failed calls and misses are not charged.

The package registers in the Integration Marketplace, stores its own enrichment records and signals, and surfaces them on customer detail pages through widget injection.

### Decisions (confirmed 2026-10-05)

| Decision | Choice | Rationale |
|---|---|---|
| Packaging | Standalone provider package, `category: 'other'`, no hub | A generic enrichment hub adds core contract surface; extract one when a second provider appears |
| Write model | Review, then accept | Third-party data never reaches CRM fields unreviewed |
| Trigger | Manual (button + bulk action); scheduled signal refresh is opt-in per company from Phase 3c | Every call costs money. A schedule counts as the user action: a user with `enrichment_treg.run` turns it on for a company, and an org admin must allow scheduling first. It runs only under the monthly budget guard |
| Distribution | `open-mercato/official-modules`, published to npm as `@open-mercato/enrichment-treg` | It is an optional plugin, not a core capability |

## Problem Statement

CRM person and company records are filled in by hand. Sales users leave Open Mercato to look up job titles, company size, industry, open roles and recent news. There is no enrichment or signals capability in the platform and no spec covering one.

## Proposed Solution

### treg endpoints

Ids, inputs and prices verified against `GET https://treg.to/catalog/search` on 2026-10-05.

| Purpose | Endpoint | Inputs | Cost per hit (USD) | Phase |
|---|---|---|---|---|
| Person profile | `treg.people.enrich` | `email`, `linkedin_url`, or `full_name` + `domain` | ~0.003 | 2 |
| Company profile | `treg.companies.enrich` | `domain`, `name`, `linkedin_url`, or `email` | ~0.002 | 2 |
| Hiring signal | `treg.companies.jobs.search` | `domain` or `name`, `limit` | 0.025–0.04 observed (catalog headline ~0.009) | 3 |
| News signal | `treg.companies.news` | `domain`, `limit` | 0.01–0.04 observed (catalog headline ~0.01) | 3 |
| Funding signal | `predictleads.companies.financing_events` (no routed endpoint exists) | `domain` | 0.04, billed per call including empty responses | 3 (off by default) |
| Email / phone finder | `treg.people.email.find`, `treg.people.phone.find` | name + domain, LinkedIn URL | ~0.005 | 4 (optional) |
| Job change | `datagma.people.job-change.detect` | name, company, title | ~0.023 | 4 (optional) |
| Similar companies | `leadsforge.companies.lookalike.preview` (direct, not routed) | `domains[]` | Free | 3d |

Routed endpoints respond with `{ output, raw, _treg: { served_by, tried, charged_micro } }`.

The rerunnable `configure-from-env` CLI command is deferred to Phase 3.

### Cost controls

- `X-Treg-Route-Max-Cost` on every call (hard ceiling enforced by treg; 402 when exceeded).
- Monthly budget enforced locally: sum of `cost_micro` for the tenant in the current month is checked before enqueueing and again in the worker.
- `Idempotency-Key` derived from the enrichment record id, so worker retries are never double-charged.
- `X-Treg-Meta: tenant=<tenantId>` for per-tenant usage attribution on the treg side.
- UI shows the estimated cost before a single or bulk run.

### User flow

1. User clicks **Enrich now** on a person or company detail tab, or selects rows and runs **Enrich selected**.
2. API creates one enrichment record per subject (`pending`) and enqueues a job. Bulk also creates a `ProgressJob` and returns `progressJobId`.
3. Worker resolves credentials, calls treg, normalizes the output, stores the result and any signals, and emits events.
4. The detail tab shows a diff of proposed versus current CRM values. The user ticks fields and clicks **Apply**.
5. Apply calls the public customers API (`PUT /api/customers/people` or `PUT /api/customers/companies`) from the widget with only the accepted fields and the subject's optimistic-lock header, so the customers update command, its ACL, audit, undo and indexing all apply unchanged. The widget then calls `POST /api/enrichment_treg/records/:id/applied` to record which fields were accepted and by whom.

Nothing is written to CRM fields outside step 5.

### Company signals (Phase 3)

Signals are dated events about a company (open roles, news, funding) shown as a timeline. They are never written to CRM fields, so there is no review step.

#### What treg returns (live calls, 2026-10-05)

| Call | Subject | Result | Served by | Charged |
|---|---|---|---|---|
| `treg.companies.news` | vlayer.xyz | 5 news events (partnerships, integrations) | `predictleads.companies.news_events`, after `akta` missed | $0.04 |
| `treg.companies.news` | openmercato.com | No articles; the body was `{ detail }` instead of `{ articles }` | — | $0 |
| `treg.companies.jobs.search` | vlayer.xyz | 2 openings (Android Engineer, iOS Engineer) | `predictleads.companies.job_openings` | $0.04 |
| `treg.companies.jobs.search` | openmercato.com | 1 opening (Remote · Wrocław) | `predictleads.companies.job_openings` | $0.04 |

What this means for the design:

- **The output contract is thin.** The routed contract only guarantees a list (`articles` for news, `jobs` for jobs) plus an optional `count`. The rows inside are whatever the serving provider returns. predictleads returns JSON:API-style rows (`{ id, type, attributes: { summary | title, … } }`). The news waterfall is `akta → predictleads`; the jobs waterfall is `leadmagic → predictleads → crustdata`.
- **Real cost is higher than the catalog headline.** A waterfall bills each provider it tries that charges for misses. Both observed hits cost $0.04, so a news + jobs refresh costs up to about $0.08 per company. The per-call ceiling (`maxCostPerCallUsd`, default 0.05) still caps a single call.
- **treg does not keep results.** `GET /calls` shows `has_result: false` for these calls. Anything not stored at call time has to be bought again.
- **A miss does not always look the same.** The documented miss is a 200 with an empty list. A company the news providers do not know returns **HTTP 404** with `{ detail: { error: 'route_caller_fault', charged_micro: 0 } }`. For signal calls only, the client maps a 404 to an uncharged `no_match` (`missOnNotFound`); profile lookups keep mapping 404 to `failed / invalid_input`.

#### Flow

1. The company Enrichment tab gets a **Signals** section with a **Refresh signals** button. Kind checkboxes (Hiring, News, and Funding when enabled in settings) sit next to it, along with the cost estimate for the selected kinds.
2. `POST /api/enrichment_treg/signals/refresh` creates one enrichment record per kind (`endpoint_id` = the kind's endpoint, same command, same statuses) and enqueues the jobs. Profile enrichment and signals stay separate calls, so a user can refresh news without paying for a profile lookup.
3. The worker calls treg with `limit` = `signalsLimit` (default 10). It stores the provider-native body in `raw_payload` and runs the signal normalizer for the provider in `served_by`, then upserts rows into `enrichment_treg_signals` deduplicated by `dedupe_hash`. It emits `enrichment_treg.signal.detected` once per refresh, with the count of new rows.
4. The timeline lists signals newest first. Each row shows type, title, date, source and a link, and can be filtered by type. A "last refreshed" line comes from the latest record per kind.
5. A refresh within 24 hours of the last completed one for the same kind asks for confirmation, because it costs money and rarely finds anything new.

People have no signals. Job changes for people stay in Phase 4.

#### Normalizer

`lib/normalize/signals.ts` maps each provider's row to `{ signalType, title, summary, url, occurredAt, location }`, keyed by `served_by`:

| Provider | Row shape | title | occurredAt | url |
|---|---|---|---|---|
| `predictleads.*` | `attributes.*` | `attributes.title` (jobs) / `attributes.summary` (news) | `attributes.found_at` / `attributes.first_seen_at` | `attributes.url` or the first source URL |
| `akta.*`, `leadmagic.*`, `crustdata.*` | Mapped from stub fixtures captured during implementation | | | |
| Unknown provider | Fallback | first of `title`, `summary`, `headline`, `name` | first of `published_at`, `posted_at`, `date`, `found_at` | first of `url`, `link`, `source_url` |

A row with no title after the fallback is dropped and counted in the record `summary` as `skippedRows`. `raw_payload` keeps the full body, so a later normalizer fix can re-derive rows without paying again.

#### Settings

| Key | Default | Notes |
|---|---|---|
| `signalsLimit` | 10 | Rows requested per call; several job providers bill per row |
| `signalsFundingEnabled` | false | Turns on the Funding kind; billed even when empty |
| `signalsScheduleEnabled` | false | Phase 3c. Allows per-company schedules in this organization; needs `enrichment_treg.configure` to change |
| `signalsScheduleMaxCompaniesPerRun` | 50 | Phase 3c. Companies refreshed per daily run; the rest wait for the next run, oldest due first |

### Scheduled signal refresh (Phase 3c)

A company can refresh its signals automatically every N days. Scheduled refresh reuses the 3a refresh path, so records, dedupe, normalizers and events are the same as a manual refresh. It depends on 3b, because the monthly budget guard must exist before anything spends money unattended.

#### Configuration

- On the company Signals section, a user with `enrichment_treg.run` sets **Refresh every [N] days** (allowed values 1, 3, 7, 14, 30; default 7), picks the kinds and saves. The section shows the next run date and the projected monthly cost (kinds × worst-case price × 30 / N).
- The control appears only when `signalsScheduleEnabled` is on for the organization. Turning that setting off pauses every schedule in the organization; per-company settings are kept.
- Turning a company's schedule off, or deleting the company, stops its refreshes. Deleted or missing companies are skipped and their schedule rows are soft-deleted by the run.

#### Mechanism

- Per-company settings live in `enrichment_treg_signal_schedules` (see Data Models), not in the scheduler. Thousands of per-company scheduler jobs would hit the scheduler's active-schedule limits and clutter its admin UI.
- Each organization with `signalsScheduleEnabled` has **one** scheduler job: `scheduleType: 'interval'`, `scheduleValue: '1d'`, `targetType: 'queue'`, `targetQueue: 'enrichment-treg-signals-scheduled'`, payload `{ tenantId, organizationId }`. A provider-owned `lib/signal-schedule-service.ts` registers and removes it through the DI `schedulerService` when the setting is toggled, the same way `data_sync`'s `createSyncScheduleService` does. The worker stays off the user-facing scheduler target list (no `schedulerSafe`), as `data-sync:scheduled` does today. Implementation must confirm that programmatic registration does not require that flag.
- The worker `workers/signals-scheduled.ts` (queue `enrichment-treg-signals-scheduled`, concurrency 1):
  1. Skips the run if the integration is disabled, credentials are missing or `signalsScheduleEnabled` is off.
  2. Selects up to `signalsScheduleMaxCompaniesPerRun` enabled schedules with `next_run_at <= now()`, oldest first.
  3. For each one, checks the budget guard with that company's estimated cost. If the budget is exhausted, it stops the run, writes one `warn` line to the integration log and leaves the remaining schedules due. It does not fail the job or retry.
  4. Otherwise it runs the `enrichment_treg.records.create` command per kind with `requestedByUserId = null` and `trigger: 'schedule'` in record metadata, enqueues the normal enrichment job and sets `last_run_at = now()`, `next_run_at = now() + interval_days`.
- A manual refresh also pushes `next_run_at` forward, so a schedule never fires right after someone refreshed by hand.
- Re-running a day's job is safe. Only rows still due are picked, and `next_run_at` is advanced in the same transaction that creates the records.

#### Notification

When a scheduled refresh stores new rows, a subscriber on `enrichment_treg.signal.detected` (only when `trigger` is `schedule`) sends an in-app notification, `enrichment_treg.signals.new`, to the user who saved the schedule. It contains the company name and new-row counts per kind and links to the company Signals section. Manual refreshes do not notify, because the user is already looking at the result.

### Similar companies (Phase 3d)

Find companies that look like a company already in the CRM, and add the ones the user picks as new CRM companies. One seed company per lookup. Lookups from several seeds at once ("companies like my top 10 customers") are out of scope; see Open questions.

#### Provider choice (live calls, 2026-10-08)

Seed `pipedrive.com`, all calls made with the project's treg token:

| Call | Result | Charged |
|---|---|---|
| `treg.companies.similar` → `tomba.companies.similar` | 12 rows: a telecom firm, a college, a Swiss club-management tool, an insurer, a restaurant, three radio stations. Rows are `{ website_url, name, industries }` | $0.0089 |
| `treg.companies.similar` preferring `companyenrich` | Skipped by treg: 5 credits ($0.049) **per company returned**, so any useful page exceeds the per-call ceiling | $0 |
| `treg.companies.similar` preferring `oceanio` | Refused with 402 `route_max_cost`: $0.162 for the default page size | $0 |
| `leadsforge.companies.lookalike.preview` | 25 rows: Attio, Insightly, Keap, noCRM, SugarCRM, Capsule, Close, Nutshell and other CRM vendors. Rows are `{ domain, name, website, industry, keywords, description, logo }`, plus `totalCount` | $0 |

The routed `treg.companies.similar` only guarantees `companies: list` (provider-native rows) and has no `limit` filter. Under the default $0.05 ceiling it effectively always lands on tomba, whose matches were unrelated to the seed. The leadsforge preview is free, returns relevant companies with descriptions, and accepts several seed domains, so 3d uses it directly. It is a direct endpoint: the body is the provider's own JSON with no `{ output, raw, _treg }` wrapper, so the client gets a `direct` mode that reads the body as the output and records the endpoint id as `served_by`.

#### Flow

1. The company Enrichment tab gets a **Similar companies** section with a **Find similar companies** button. The lookup is free, so there is no cost line and no re-run confirmation.
2. `POST /api/enrichment_treg/lookalikes/refresh` normalizes the company's domain (or the host of its website; 422 `missing_identity` when neither exists), creates one enrichment record (`subject_type: 'company'`, `endpoint_id: 'leadsforge.companies.lookalike.preview'`, `identity: { domains: [seed] }`) through `enrichment_treg.records.create`, and enqueues the usual job. Record lifecycle, idempotency key, failure mapping and integration-log reporting are the Phase 2 ones.
3. The worker stores the body in `raw_payload`, normalizes the rows and inserts new ones into `enrichment_treg_lookalikes`, deduplicated per seed by `dedupe_hash`. The seed's own domain and rows without a name or valid domain are dropped (the latter counted as `skippedRows`). At most 25 rows are kept per lookup, in provider order. Rows found again only get `last_seen_at` bumped; their status never changes. New rows are then matched against the CRM (below). The record `summary` is `{ newCount, totalCount, skippedRows, crmMatchSkipped }`.
4. The section lists the rows newest first: name, domain (external link), industry, a two-line description and a status badge: **New**, **In CRM** or **Added** (both with an "Open in CRM" link) and **Dismissed** (hidden behind a "Show dismissed" toggle). It reloads on `enrichment_treg.record.*` events and polls while a lookup is running, like signals.

#### Adding companies to the CRM

1. The user ticks one or more **New** rows and clicks **Add to CRM (n)**. A confirmation dialog lists the companies and the fields that will be set.
2. The widget re-reads the selected rows (`GET /lookalikes?ids=…`), which re-runs the CRM match. Rows that are no longer **New** are skipped and counted.
3. For each remaining row, the widget calls the public `POST /api/customers/companies` with `displayName` and `brandName` (name), `domain`, `websiteUrl`, `industry` and `description`. The customers create command, its ACL (`customers.companies.manage`), audit, undo and indexing apply unchanged.
4. With the returned company id, the widget calls `POST /api/enrichment_treg/lookalikes/:id/imported` with `{ companyId }` and the row's `updatedAt` as the optimistic-lock header. That runs `enrichment_treg.lookalikes.mark_imported` (undoable: restores the previous status and fields).
5. Rows run one at a time; failures are counted and the rest continue. The result is reported as added / skipped / failed flash messages. If the company was created but marking failed, the next read matches the new company by domain and shows the row as **In CRM**, so a retry does not create it twice.
6. **Add to CRM** and the row checkboxes are shown only when `GET /lookalikes` reports `canImport` (the caller has `customers.companies.manage`).

**Dismiss** (`POST /api/enrichment_treg/lookalikes/:id/dismiss`, command `enrichment_treg.lookalikes.dismiss`, undoable, optimistic lock on `updatedAt`) hides a **New** or **In CRM** row. Dismissed rows stay dismissed when a later lookup finds them again. Added rows cannot be dismissed (409).

#### Matching against the CRM

A row is **In CRM** when an existing, non-deleted company in the same organization has the same normalized domain (lowercased, without protocol, `www.` and path) in `domain` or in the host of `websiteUrl`. The seed company itself never counts as a match.

The customers module encrypts `domain` and `website_url` and has no hash column, so the match cannot be a SQL filter. `loadCrmDomainIndex` counts the organization's company profiles, reads them in batches of 500 with `findWithDecryption` and builds a domain → company id map. It runs when a lookup completes and on every `GET /lookalikes` that returns **New** or **In CRM** rows; changed statuses are written back. An **In CRM** row whose company was deleted returns to **New**. Above 20,000 profiles the scan is skipped: rows stay as they are, `crmMatchSkipped: true` is returned, and the section shows a warning. A cache was considered and left out: lookups and reads are user-triggered and rare, and a cache would need invalidation on customers events. A proper fix is a domain hash column in customers, which is a core change and out of scope here.

#### Normalizer

`lib/lookalikes.ts` maps each row to `{ name, domain, websiteUrl, industry, description }`: name from `name`, `company_name` or `title`; domain from `domain`, `website`, `website_url` or `url` (host only); website from `website`/`website_url`, else `https://<domain>`; industry from `industry` or the first of `industries`; description from `description` or `summary`. That covers the leadsforge rows and, for a later provider switch, the tomba row shape. `dedupe_hash` is sha256 of the normalized domain. The raw row is kept in `payload`, so a later normalizer fix can re-derive values without another call. A trimmed leadsforge response is committed as the test fixture `__tests__/fixtures/leadsforge-lookalike-preview.json`.

#### Open questions

- leadsforge documents the preview as a way to shape filters "before paying for the same query on the search route". If it gets rate-limited or reduced, the fallback is `leadsforge.companies.lookalike.search` (~$0.0245 per row) or `oceanio.companies.lookalike` (~$0.016 per row), both of which need a cost estimate in the UI.
- Should a later phase add multi-seed lookups (the preview already accepts several `domains`) from a bulk action on the companies list, and the preview's filters (`employeeRanges`, `locations`, `categories`)?

### Commands, scope and permissions

- Record creation and "mark applied" run through the command bus as `enrichment_treg.records.create` and `enrichment_treg.records.mark_applied`. Both are undoable: undoing a create soft-deletes the record; undoing mark-applied restores the previous `applied_fields`, `applied_at` and `applied_by_user_id` from the snapshot.
- Worker status transitions (`pending → running → completed | no_match | failed`) are direct writes to the record, the same way job-progress rows are updated; they are system state of a background job, not user edits.
- Every route resolves scope with `resolveOrganizationScopeForRequest` and uses its `tenantId` and `selectedId`. Write routes return 403 `organization_selection_rejected` when the requested organization was rejected.
- Besides the module feature, every route checks the caller can view the subject: `customers.people.view` for people, `customers.companies.view` for companies (403 `forbidden`).
- A record left in `running` for more than 5 minutes (worker crash) is resumed on the next delivery; the record-derived `Idempotency-Key` keeps treg from charging twice.
- Failed lookups are written to the integration log at `error` level, which reaches `reportError` and shows on the integration's Logs tab. Logging failures degrade to a warning.

### Coupling to `customers`

- Read: when an enrichment is requested, the route reads the subject's email, LinkedIn URL, names and company domain (or company domain, website, name) with `findOneWithDecryption` on the customers entities, tenant and organization scoped. The resulting lookup identity is stored on the record, so the worker never reads customers data.
- Write: only through the public customers CRUD API, which runs `customers.people.update` / `customers.companies.update` (audit, undo, indexing and optimistic locking preserved; the apply call passes the subject's `updatedAt`). The module never writes customers tables.
- UI: widget injection only. No imports from customers internals, no ORM relations — subject references are FK ids.

### Client behaviour

| treg response | Outcome |
|---|---|
| 200 | `completed`; cost from `X-Treg-Cost-Micro`, provider from `X-Treg-Served-By`, call id from `X-Treg-Call-Id` |
| 200 with empty `output` | `no_match` (not charged) |
| 402 | `failed` with reason `out_of_balance` or `max_cost_exceeded`; not retried |
| 429, 503, 409, 5xx, network error | `failed` with reason `provider_unavailable`; the user re-runs it (automatic backoff retry is Phase 3) |
| Other 4xx | `failed` with reason `invalid_input`; not retried |

The token is resolved fresh from `integrationCredentialsService.resolve('enrichment_treg', scope)` on every job and never logged. Errors are recorded through `integrationLogService` and `reportError`.

### Events

| Event id | When | Flags |
|---|---|---|
| `enrichment_treg.record.completed` | A record reaches `completed` or `no_match` | `clientBroadcast: true` |
| `enrichment_treg.record.failed` | A record reaches `failed` | `clientBroadcast: true` |
| `enrichment_treg.record.applied` | A proposal is applied to the CRM | — |
| `enrichment_treg.signal.detected` | Phase 3a: a signals refresh stored at least one new (non-duplicate) row; payload carries `subjectId`, `signalType`, `newCount` | `clientBroadcast: true` |

### ACL

| Feature | Grants | Default roles |

### Normalized proposal fields

| Subject | Fields |
|---|---|
Mapped from treg's routed output contracts (`src/treg/catalog/contracts.yaml` in superdesigndev/treg):

| Subject | treg output → CRM field | Display only |
|---|---|---|
| Person | `title` → `jobTitle`, `linkedin_url` → `linkedInUrl` | `full_name`, `company`, `company_domain`, `location` |

## API Contracts

All routes are tenant and organization scoped, export `openApi`, validate with zod, and run the mutation guard registry on writes.

| Method | Path | Feature | Status | Purpose |
|---|---|---|---|---|
| POST | `/api/enrichment_treg/enrich` | `run` | Done | Body `{ subjectType, subjectId }`; returns `{ record }` (202) |
| GET | `/api/enrichment_treg/records` | `view` | Done | Query `subjectType, subjectId, page, pageSize ≤ 100`; paged list, newest first, including `updatedAt` |
| POST | `/api/enrichment_treg/records/:id/applied` | `run` | Done | Body `{ fields: string[] }`; records fields the user applied through the customers API; returns `{ record }` |
| POST | `/api/enrichment_treg/enrich/bulk` | `run` | Phase 3 | Body `{ subjectType, subjectIds (max 100) }`; returns `{ progressJobId, recordIds }` |
| GET | `/api/enrichment_treg/estimate` | `run` | Phase 3 | Returns `{ estimatedCostMicro, remainingBudgetMicro }` |
| POST | `/api/enrichment_treg/signals/refresh` | `run` | Phase 3 | Body `{ subjectId, kinds: ('hiring' \| 'news' \| 'funding')[] }`, company only; returns `{ records }` (202). 422 `signal_kind_disabled` for funding when it is off |
| GET | `/api/enrichment_treg/signals` | `view` | Phase 3 | Query `subjectType, subjectId, signalType?, page, pageSize ≤ 100`; newest `occurred_at` first, then `first_seen_at` |
| GET | `/api/enrichment_treg/usage` | `configure` | Phase 3 | Returns `{ balanceMicro, monthToDateMicro, monthlyBudgetMicro }` |
| GET | `/api/enrichment_treg/signals/schedule` | `view` | Phase 3c | Query `companyId`; returns `{ schedule \| null, scheduleAllowed, projectedMonthlyCostMicro }` including `updatedAt` |
| POST | `/api/enrichment_treg/lookalikes/refresh` | `run` | Phase 3d | Body `{ companyId }`; returns `{ record }` (202). 422 `missing_identity` when the company has no domain or website |
| GET | `/api/enrichment_treg/lookalikes` | `view` | Phase 3d | Query `companyId`, `status?`, `ids?` (comma-separated, ≤ 100), `page`, `pageSize ≤ 100`; returns rows with `updatedAt`, `latest` lookup record, `canImport`, `crmMatchSkipped`. Re-runs the CRM match for `new` and `in_crm` rows |
| POST | `/api/enrichment_treg/lookalikes/:id/imported` | `run` | Phase 3d | Body `{ companyId }`; command `enrichment_treg.lookalikes.mark_imported` (undoable). The company must exist in the same organization (404 `subject_not_found`); 404 `lookalike_not_found`; 409 `record_not_applicable` unless the row is `new`; 409 on a stale optimistic-lock header |
| POST | `/api/enrichment_treg/lookalikes/:id/dismiss` | `run` | Phase 3d | Command `enrichment_treg.lookalikes.dismiss` (undoable); 409 `record_not_applicable` for `imported` rows; 409 on a stale optimistic-lock header |
| PUT | `/api/enrichment_treg/signals/schedule` | `run` | Phase 3c | Body `{ companyId, isEnabled, intervalDays, kinds }`; upsert via command `enrichment_treg.signal_schedules.save` (undoable); optimistic lock on `updatedAt`. 422 `schedule_not_allowed` when `signalsScheduleEnabled` is off |

Errors use `{ error: <code> }`: 400 `validation_failed`, 401 `unauthorized`, 403 missing feature, 404 `subject_not_found` / `record_not_found`, 409 `record_not_applicable`, 422 `integration_disabled` / `integration_not_configured` / `missing_identity`. Optimistic-lock conflicts during apply come from the customers API (409) and surface on the standard conflict bar. Phase 3 adds 402 for the local budget guard.

## Implementation Phases

## Test Plan

Unit tests use Jest (`jest.config.cjs`), matching the modules repo, not Vitest.

### Unit (`__tests__/`)

- Client: headers sent (`X-Treg-Token`, `Idempotency-Key`, `X-Treg-Route-Max-Cost`, `X-Treg-Meta`), cost and provider captured, every row of the client behaviour table, missing token throws.
- Normalizers: full, partial and empty outputs for person and company; signal dedupe hash stability.
- Lookalike normalizer (`lookalikes.test.ts`): leadsforge fixture, tomba-style fallback fields, rows without name or domain dropped and counted, seed and duplicate domains dropped, row limit, request body from domain or website.
- CRM match: domain and website-host index, `new` ↔ `in_crm` transitions, seed ignored, dismissed and imported rows untouched; worker branch stores, matches and skips the match above the scan cap (`enrichment-service.test.ts`).
- Lookalike commands (`lookalike-commands.test.ts`): mark-imported and dismiss with undo, 404/409 cases, stale and matching optimistic-lock headers.
- Client: `direct` endpoints read the unwrapped body and report the endpoint as provider.
- Signal normalizer: a fixture per provider (predictleads news and jobs from the 2026-10-05 live calls, with names and URLs anonymized), unknown-provider fallback, rows without a title dropped and counted.
- Budget guard: under, at and over budget; unlimited when unset.
- Preset: env vars map to credentials; no-op when unset.

## Risks & Impact Review

| Risk | Scenario | Severity | Affected area | Mitigation | Residual |
|---|---|---|---|---|---|
| Uncontrolled spend | A user bulk-enriches thousands of rows | High | Tenant treg balance | 100-row bulk cap, per-call max cost, monthly budget, cost shown before run | Low |
| Double charging | Worker retries after a timeout | Medium | Billing | `Idempotency-Key` per record (24 h retention on treg) | Low |
| Personal data sent to a third party | Emails and names leave the platform | High | GDPR | Integration disabled by default; manual triggers only; documented in package docs; raw payload and proposal encrypted at rest | Medium — tenant must have a lawful basis |
| Wrong data written to CRM | Provider returns a different person | Medium | CRM data quality | Review-then-accept; no silent overwrite; apply goes through undoable commands | Low |
| Provider-native output drift | A routed provider changes its shape | Medium | Normalizers | Tolerant zod parsing, raw payload retained, `served_by` recorded | Low |
| treg unavailable or saturated | 503 during a bulk run | Low | Bulk jobs | Backoff honouring `Retry-After`; record marked `failed` after retries; rerun is idempotent per record | Low |
| First `category: 'other'` provider | Marketplace UI assumes a hub | Low | Integrations admin UI | Verify listing and detail pages in Phase 1; types already allow it | Low |
| Platform version skew | The modules repo pins an older platform than core `develop`; `carrier-inpost` still declares MikroORM `^6.5.9` while core has moved to v7 decorators | Medium | Entities, migrations, build | Run `yarn platform:sync` first and write entities against the ORM version the sandbox actually resolves; choose the peer range from that | Low |
| Extension spots missing in the pinned platform | `detail:customers.*:tabs` or the list bulk-action spots differ in the platform version the modules repo targets | Medium | UI | Verify each spot id in the sandbox in Phase 1 before building widgets | Low |
| Review latency | The modules repo has one published module and was last pushed 2026-07-31 | Low | Release date | Open a draft PR early and tag maintainers; the package also works unpublished through the submodule path | Medium |
| Signal cost above estimate | Waterfall bills a missing provider before the one that hits; observed $0.04 per signal call against a ~$0.01 catalog headline | Medium | Tenant treg balance | Estimate uses the routing plan's worst case (sum of billed-miss children up to the per-call ceiling), not the headline; 24 h re-refresh confirmation; funding off by default | Low |
| Provider-native signal rows | Routed contract only guarantees a list; row fields differ per provider and can change | Medium | Signals timeline | Normalizer keyed on `served_by` with a generic fallback; raw body kept for re-derivation; rows without a title dropped, not guessed | Low |
| Unattended spend | Schedules on many companies keep charging after users stop looking | High | Tenant treg balance | Org-level opt-in by `configure`; monthly budget guard checked per company before each scheduled call; per-run company cap; projected monthly cost shown when saving; minimum interval 1 day | Low |
| Silent schedule failure | Budget exhausted or credentials revoked, so schedules stop without anyone noticing | Medium | Signal freshness | Warning in the integration log; "last refreshed" date and next run shown on the Signals section; schedules stay due and resume once the cause is fixed | Medium — no proactive alert until a notification for this is added |
| Lost paid results | treg does not retain call results (`has_result: false`) | Low | Billing | Store `raw_payload` before normalizing, in the same write that marks the record `completed` | Low |
| Duplicate CRM companies | A lookalike is added while the same company already exists, or two users add it at once | Medium | CRM data quality | Rows re-matched by domain right before Add to CRM, `in_crm` rows cannot be added, match cache cleared on customers company events | Medium — two simultaneous adds can still both succeed; customers has no unique domain constraint |
| Slow CRM match | Organizations with tens of thousands of companies; domain is encrypted, so matching decrypts every profile | Medium | Lookalikes list latency | Batched scan, only when the page has `new` or `in_crm` rows, 20,000-profile cap with a visible warning | Medium until customers gets a domain hash column |
| Free provider changes terms | leadsforge limits or prices the preview, which it documents as a step before its paid search | Medium | Similar companies | Failures land on the record and the integration log like other lookups; normalizer already reads other providers' row shapes; paid fallbacks listed in Open questions | Medium |
| Poor matches | A provider returns companies unrelated to the seed (tomba did for pipedrive.com) | Medium | User trust, CRM data quality | Provider chosen on a live comparison; nothing is added to the CRM without review; Dismiss | Low |
| Cross-tenant leakage | Record fetched by id without scope | High | Security | Every query filters tenant and organization; integration tests cover cross-tenant ids | Low |
